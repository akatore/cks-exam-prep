### The Improved Question

**Scenario: Securing Kubelet and Etcd Components**

**Context:**
A recent CIS Benchmark security scan was performed against your `kubeadm`-provisioned Kubernetes cluster. The scanning tool identified several critical misconfigurations in the control plane components that need immediate remediation.

**Task:**
Resolve the identified security violations by updating the configuration files for the affected components and ensuring the new settings take effect. The cluster currently uses Docker Engine (or Containerd) as its container runtime.

**Requirements:**

1. **Kubelet Misconfigurations:**
* Disable anonymous authentication (ensure `anonymous-auth` is set to `false`).
* Ensure the authorization mode is not set to `AlwaysAllow`. Configure it to use `Webhook` for both authentication and authorization where possible.


2. **Etcd Misconfigurations:**
* Enable client certificate authentication (ensure `--client-cert-auth` is set to `true`).



---

### The Solution

In a `kubeadm` cluster, the Kubelet configuration is primarily managed via a configuration file (usually `/var/lib/kubelet/config.yaml`), while control plane components like `etcd` run as Static Pods managed by manifests in `/etc/kubernetes/manifests/`.

#### Step 1: Fix the Kubelet Violations

For `kubeadm` clusters, Kubelet parameters are passed via a YAML configuration file rather than command-line flags.

1. **Edit the Kubelet configuration file:**
Open the file using your preferred text editor (e.g., `vi` or `nano`):
```bash
sudo vi /var/lib/kubelet/config.yaml

```


2. **Update Authentication and Authorization:**
Find the `authentication` and `authorization` blocks. Update them to match the following requirements (disable anonymous auth and set authorization to Webhook):
```yaml
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration
# ... [other settings] ...
authentication:
  anonymous:
    enabled: false  # Changed to false
  webhook:
    cacheTTL: 0s
    enabled: true   # Ensure webhook auth is enabled
  x509:
    clientCAFile: /etc/kubernetes/pki/ca.crt
authorization:
  mode: Webhook     # Changed from AlwaysAllow to Webhook
  webhook:
    cacheAuthorizedTTL: 0s
    cacheUnauthorizedTTL: 0s
# ... [other settings] ...

```


3. **Restart the Kubelet service:**
For the changes to take effect, restart the systemd service:
```bash
sudo systemctl daemon-reload
sudo systemctl restart kubelet
sudo systemctl status kubelet

```



#### Step 2: Fix the Etcd Violations

`etcd` runs as a static pod. If you modify its manifest, the Kubelet will automatically detect the change and restart the pod.

1. **Edit the Etcd static pod manifest:**
```bash
sudo vi /etc/kubernetes/manifests/etcd.yaml

```


2. **Add the required argument:**
Locate the `spec.containers.command` section. Add `--client-cert-auth=true` to the list of commands:
```yaml
spec:
  containers:
  - command:
    - etcd
    - --advertise-client-urls=https://192.168.1.10:2379
    - --cert-file=/etc/kubernetes/pki/etcd/server.crt
    - --client-cert-auth=true  # <-- Add this line
    - --data-dir=/var/lib/etcd
    # ... [other arguments] ...

```


3. **Verify the Etcd pod restarts:**
Because you edited a static pod manifest in the watched directory, Kubelet will automatically terminate the old `etcd` pod and start a new one. Verify that it comes back up successfully:
```bash
kubectl get pods -n kube-system | grep etcd

```


*Note: If the pod crashes (CrashLoopBackOff), double-check your YAML indentation in `etcd.yaml` and ensure there are no typos in the flag.*

Here are the command-line snippets to quickly verify that your changes have been successfully applied to the running components.

### 1. Verifying Kubelet Settings

Since `kubeadm` passes the bulk of its configuration to the Kubelet via a YAML file rather than command-line arguments, the best way to verify is to check the configuration file that the running Kubelet process is actively using.

First, verify the location of the Kubelet config file from the running process:

```bash
ps aux | grep kubelet | grep --color=auto "\--config"

```

*(This will typically output something like `--config=/var/lib/kubelet/config.yaml`)*

Next, quickly `grep` that file to confirm your authentication and authorization settings are correct:

```bash
grep -A 2 -E 'anonymous:|authorization:' /var/lib/kubelet/config.yaml

```

**Expected Output:** You should see `enabled: false` under `anonymous:`, and `mode: Webhook` under `authorization:`.

### 2. Verifying Etcd Settings

Because `etcd` runs as a Static Pod, its command-line arguments are passed directly to the container process. You can verify this in two ways:

**Method A: Check the running processes on the control plane node**

```bash
ps aux | grep etcd | grep --color=auto "client-cert-auth"

```

**Expected Output:** The command should return the `etcd` process string highlighting `--client-cert-auth=true`.

**Method B: Check the Pod definition via kubectl**
Replace `<your-node-name>` with the name of your control plane node (e.g., `etcd-master-node`):

```bash
kubectl get pod -n kube-system -l component=etcd -o jsonpath='{.items[*].spec.containers[*].command}' | grep --color=auto "client-cert-auth"

```

**Expected Output:** This will print the array of commands passed to the Etcd container, and you should clearly see `--client-cert-auth=true` in the output.
