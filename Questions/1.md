Here is the step-by-step process to enforce the AppArmor profile on the worker node, configure the Pod manifest, and deploy it.

### Step 1: Enforce the AppArmor Profile on `node-01`

First, you need to load the prepared AppArmor profile into the kernel of the specific worker node.

1. **SSH into the worker node:**
```bash
ssh node-01

```


2. **Load the AppArmor profile:**
Assuming the prepared profile is located at `/etc/apparmor.d/nginx-profile-2` (a standard location, though adjust the path if yours is stored elsewhere), run the `apparmor_parser` command to enforce it:
```bash
sudo apparmor_parser -q /etc/apparmor.d/nginx-profile-2

```


3. **Verify the profile is loaded:**
```bash
sudo aa-status | grep nginx-profile-2

```


*(It should appear under the "profiles are in enforce mode" section).*
4. **Exit the node** to return to your control plane/master node:
```bash
exit

```



---

### Step 2: Edit the Pod Manifest

Next, define a Pod manifest that targets `node-01` and references the AppArmor profile.

Create a file named `pod.yaml` and add the following configuration.

> **Note:** The annotation key must match the container name. In this example, the container is named `nginx`, so the annotation is `container.apparmor.security.beta.kubernetes.io/nginx`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-nginx-pod
  annotations:
    # Tell Kubernetes to use the AppArmor profile loaded on the localhost (node)
    container.apparmor.security.beta.kubernetes.io/nginx: localhost/nginx-profile-2
spec:
  # Ensure the pod is scheduled strictly on node-01 where the profile is loaded
  nodeName: node-01 
  containers:
  - name: nginx
    image: nginx:latest
    ports:
    - containerPort: 80

```

*(Note: If you are using Kubernetes v1.30 or newer, AppArmor is generally available, and you can specify it directly under `securityContext.appArmorProfile` instead of using annotations.)*

---

### Step 3: Deploy and Verify

1. **Deploy the Pod:**
```bash
kubectl apply -f pod.yaml

```


2. **Verify the Pod is running:**
```bash
kubectl get pods secure-nginx-pod -o wide

```


The status should be `Running`, and it should show `node-01` as the node.
3. **Ensure the profile was applied correctly:**
Describe the Pod to check for any AppArmor-related errors in the events:
```bash
kubectl describe pod secure-nginx-pod

```


If the profile wasn't found or couldn't be applied, you would see a `CreateContainerError` or a warning in the Events section at the bottom. Since it is running, it successfully attached the profile.

Would you like me to explain how to verify the profile is actively blocking restricted actions inside the container once it's running?

Here is how you can verify that your AppArmor profile is actively doing its job and restricting actions inside the Pod.

To test it, you need to attempt an action that the `nginx-profile-2` is specifically configured to block (like writing to a protected directory or executing a restricted shell).

### Step 1: Attempt a Restricted Action

Use `kubectl exec` to run a command directly inside the container.

A common restriction in AppArmor profiles is preventing writes to the `/root` or `/etc` directories. Let's try to create a file in the root directory:

```bash
kubectl exec secure-nginx-pod -- touch /root/test.txt

```

**Expected Outcome:** If the profile blocks file writes to `/root`, you will receive an error message directly in your terminal, like this:

> `touch: cannot touch '/root/test.txt': Permission denied`
> `command terminated with exit code 1`

*(Note: If your profile restricts other things—like blocking `sh` or network access—you would test those specific actions instead.)*

---

### Step 2: Check the Kernel Audit Logs on the Node

To definitively prove that AppArmor (and not standard Linux file permissions) blocked the action, you can check the system logs on the worker node where the Pod is running.

1. **SSH back into the worker node:**
```bash
ssh node-01

```


2. **Check the logs for AppArmor denial messages:**
AppArmor logs its activity to the system audit log or kernel ring buffer. Run the following command to search for `DENIED` events related to your profile:
```bash
sudo dmesg | grep apparmor | grep DENIED

```


*Alternatively, check the audit log if `auditd` is running:*
```bash
sudo grep apparmor /var/log/audit/audit.log | grep DENIED

```



**Expected Outcome:**
You should see a log entry confirming the block. It will look something like this:

> `audit: type=1400 audit(1710330000.000:123): apparmor="DENIED" operation="file_perm" profile="nginx-profile-2" name="/root/test.txt" pid=4567 comm="touch" requested_mask="w" denied_mask="w" fsuid=0 ouid=0`

This log tells you exactly what happened: the `nginx-profile-2` profile blocked a `touch` command from getting write (`w`) access to `/root/test.txt`.

Would you like me to walk through how to troubleshoot if a profile is accidentally blocking legitimate traffic and causing the Pod to crash?

When an AppArmor profile is too restrictive, it often results in the application crashing on startup (`CrashLoopBackOff`) or failing to serve traffic because it cannot read a necessary configuration file, bind to a port, or execute a required binary.

Here is the standard methodology for troubleshooting and fixing an overly strict profile without guessing what went wrong.

### Step 1: Confirm the Pod's Symptoms

First, check the application logs to see if the container is explicitly throwing a "Permission denied" error.

```bash
kubectl logs secure-nginx-pod

```

If the application crashes before logging anything useful, or if you suspect AppArmor is silently dropping access, you need to use AppArmor's built-in debugging mode.

---

### Step 2: Switch the Profile to "Complain" Mode

AppArmor has two modes: **Enforce** (blocks and logs) and **Complain** (allows the action, but logs that it *would* have blocked it). Switching to Complain mode lets your Pod run normally while telling you exactly what rules you are missing.

1. **SSH into the worker node** where the profile is loaded (`node-01`).
```bash
ssh node-01

```


2. **Put the profile into Complain mode:**
*(Note: This requires the `apparmor-utils` package to be installed on the node).*
```bash
sudo aa-complain /etc/apparmor.d/nginx-profile-2

```


*If you don't have `aa-complain`, you can edit the profile file directly, change the `flags=(enforce)` line (if present) to `flags=(complain)`, and reload it using `sudo apparmor_parser -r /etc/apparmor.d/nginx-profile-2`.*

---

### Step 3: Trigger the Legitimate Traffic

With the profile in Complain mode, restart your Pod so it picks up the profile change, or simply let it run if it was previously crash-looping.

Execute the actions or send the traffic that was previously failing. Because AppArmor is no longer blocking anything, the application should now work perfectly.

---

### Step 4: Check the Node Logs for "ALLOWED" Events

Now, find out what AppArmor flagged while the app was running successfully.

1. **Search the kernel logs** for AppArmor events marked as `ALLOWED` instead of `DENIED`:
```bash
sudo dmesg | grep apparmor | grep ALLOWED

```


2. **Analyze the output:**
You will see log entries showing exactly what the application requested. For example:
> `apparmor="ALLOWED" operation="file_mmap" profile="nginx-profile-2" name="/var/cache/nginx/client_temp" ... requested_mask="w" ...`


This log tells you that Nginx needed write (`w`) access to `/var/cache/nginx/client_temp`, which was missing from your original profile.

---

### Step 5: Update the Profile and Re-enforce

1. **Edit the profile** on the node to include the missing permissions based on the audit logs.
```bash
sudo nano /etc/apparmor.d/nginx-profile-2

```


Add the necessary rule (e.g., `/var/cache/nginx/** rw,`).
2. **Put the profile back into Enforce mode:**
```bash
sudo aa-enforce /etc/apparmor.d/nginx-profile-2

```


*(Or reload it with `sudo apparmor_parser -r /etc/apparmor.d/nginx-profile-2`).*

Restart the Pod one last time to ensure it runs cleanly under the newly fixed, enforced profile.
